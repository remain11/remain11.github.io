## 第二课 提示词工程

![image-20260913183048889](/notes/generative-software-engineering/image-20260913183048889.png)

- **提示词工程就是上下文工程**——先搞清楚上下文里有什么，每个部分会把模型带向何方
  - Agent上下文构成
    - **System Prompt（系统提示词）**：由 Agent 外壳（harness，如 Codex、Claude Code 等）内建注入；
    - **agents.md**：全局级与项目级的用户自定义指令，可以层层嵌套；
    - **技能（Skills）索引**：模型只能看到每个技能的元数据（名称与简短描述），完整的 SKILL.md 只在任务匹配时按需加载，使用完毕后从上下文中移除；
    - **工具定义**：所有可调用的工具以文本形式直接出现在上下文里；
    - **会话历史与工具调用结果**：每一次工具调用及其返回结果都线性地追加进上下文；
    - **环境注入**：每一轮执行都会注入当前环境信息，例如所用模型、当前时间等。
  - 利用AI进行费曼学习法
  - 任何软件工程任务都可以抽象为三段：**意图（Intent）→ 规格（Specification）→ 实现（Implementation)**
  - 写prompt最重要的是verifier

- **Verifier 是第一原则**——给模型明确的验证信号，它就能不知疲倦地逼近正确；注意力的规律决定了规则要"能被看到"，也要警惕上下文污染；
  - 用AI读论文：不是直接总结论文，而是先让AI与人对齐，再推理
    - **对齐立场**：审稿时讲者会先写一段 prompt 声明自己的立场与评审标准；对学生而言，要维护一份"个人知识库"（agents.md 或 memory），告诉 AI"我的计算机系统基础学到什么程度、我的编程水平是什么"；
    - **重构**：让 AI 用你已有的知识把论文内容重新讲一遍。
    - **一步推理**：这是 AI 最擅长的——思维链本来就是根据过去所有事实向后推一步，而这一步**可以 verify**。
- **长程任务中人依然关键**
  - **长程任务意味着不确定性**：从初始状态出发，只有一个模糊的意图，规格与实现都不清楚，最终目标是交付一个高质量的实现。
  - 把开放问题分解为可验证的子问题（算力换智力），把有限的精力留给收益最大的事，其余放手交给 AI



## 第三课 软件仓库管理



![image-20260924124033576](/notes/generative-software-engineering/image-20260924124033576.png)

- Virtual Implementation：一种适用于任何课程的学习方法

- 使用 git 的 bad practice
  - commit message 无信息量
  - 加入 编译产物文件
  - 加入不通用的配置文件 .vscode .DS_Store 等等
  - 加入日志目录 log
  - 暴露API KEY
- Hook：把规范固化成自动检查
  - 比如可以让 ai 询问的时候，自动触发“叮”的时候提醒
  - 比如可以自动ci

- Git 的底层数据结构：目录树
  - blob / tree / commit 类型的 object

- jyy的多 Agent 工作流
  - **第一阶段：架构设计用单线程，用一个智力比较高的模型跟它讨论。** 这个其实很重要，因为如果你的软件设计得不好，你后面就是无穷的迭代。
    - **绝大部分的接口都设置成 functional 的，就是 pure function**，包括我的 trace 是程序的一个 pure function；
    - 我有一个标准的程序 **derivation graph**，要求按照这种方式来展开；
    - **所有全局互相影响的状态都注册到一个全局的地方**：比如光标的位置会怎么样影响这个可视化、包括菜单条——这是非常干净、非常小的状态。
    - 还会直接要求 agent：在设计这些 visualization 的时候，**禁止看任何库函数的实现，只看接口**。所以它非常省 token——就几万个 token 就可以做一个这样的 playground。
  - **第二阶段：架构完成以后，开三个（或几个）terminal 并行。**



## 第四课 软件仓库管理 (2)

- Lab1：实现一个个人成长助手
- 文件系统的历史包袱与技术债：文档与 code 不一致
- git merge VS git rebase
  - merge 有一个专门的 merge 节点，如果发生冲突，解决后可能导致作者信息改变
  - rebase 可以解决这个问题，会将 feature 线性追加到 master上，如果有冲突，需要逐个解决
- Jujutsu
  - 引入change这个概念，冲突也是change，不存在必须处理的中间态，change id，永远固定不变
  - 去除了 staging 区
- 利用worktree 可以建多个工作区，避免用 stage 或者临时commit
- llm会过度遵循这个指令，最终导致它会生成一个确实满足了指令、但是其实不是你想要的东西
- 如何抵抗未来需求发生根本性的变化，使用 git建repository



## 第五课 软件工程的来龙去脉

- jev，一个可以输出结构化信息的模型，可以快速的做判断做选择
- intent → spec → implementation：软件就是这三者之间的 gap
  - **intent**：你想要什么；
  - **specification**：架构、接口、约束；
  - **implementation**：真正跑起来的代码。
- 直接做一个 **Minimum Viable Product（MVP）**，一个最小原型。
  - 做一个统一 各种设备接口的 self-serive，用户可以无安装、无细致了解设备具体信息，可以直接表达意图，能够验收，并且能够被大模型调用的接口服务
  - 比如可以直接避免用各个厂商开发的软件
  - 让个人助手驱动物理设备
- 瀑布模型的失败
  - 测试是链条上第一个物理事件
- 用 AI 读一手资料：知识的有损压缩不再必要
